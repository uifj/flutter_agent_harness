# ADR-0065: 恢复前先留可回滚副本

- **状态**: ACCEPTED
- **分类**: DEF
- **优先级**: P2
- **影响维度**: 生产功能
- **日期**: 2026-10-04
- **来源**: kelivo 评估 §7 B9（kelivo 的 restore 流水线：cutover 前把当前活库打成 previous bundle，失败自动回滚，"恢复前先备份"是它的 README 明文承诺）。本仓库的 restore 是**不可逆覆盖**——ADR-0042 保证了"写进去的都是验过名的"，但没有保证"写错了的还能回来"。
- **修复 commit**: 本批（见登记表行回填）

## 背景（Context）

`restoreBackup`（`lib/state/backup_service.dart:105-142`）在条目名全部验过后逐条覆盖。用户选错归档（旧设备的、别的项目的）、或归档内容与预期不符时，**当前数据已被覆盖且无处可寻**——这是"恢复"这个动作里唯一没有出口的地方。kelivo 的答案是把"恢复前先备份"做成机制：cutover 前自动留 previous bundle，失败回滚，成功后归档保留几代。

## 决策（Decision）

**restore 的第一个字节写下之前，把会被触碰的现有文件原样拷进 `<support>/pre-restore/` 快照；恢复成功后保留最近 3 份。**

1. **只拷会被触碰的**（zip 里的条目集合），不整目录快照——恢复是逐文件覆盖，回滚面就是那些文件；没被触碰的数据（新会话、新技能）不属于"恢复前的世界"，混进来反而让回滚副本说谎。
2. **目录结构原样镜像**（`pre-restore/<stamp>/<relative-path>`），回滚 = 把快照目录拷回原位——不需要索引文件，文件系统布局就是清单。
3. **保留 3 份**（stamp 排序，最旧的删）；强杀进程最多损失"这份副本"，不影响主数据。3 份而不是 kelivo 的更复杂 GFS：本地小数据（session sidecar + 布局 JSON）单份量级 MB，三份足够"刚恢复完发现选错了"的场景。
4. **失败语义不变**：条目名越界仍然整体抛（ADR-0042 的"半恢复不可见也不可退"），快照在抛之前不建——副本只服务于"恢复成功但选错了"和"恢复中途失败"两种情况。
5. **UI 顺带一格**：设置页 Backup 节加"恢复前快照"行为说明行 + 打开文件夹入口（`onOpenPreRestoreFolder`，与诊断文件夹同款 reveal 缝）。
6. **明确不做**：回滚 UI 按钮（快照的消费者是文件管理器——恢复是显式动作，回滚也该是；做成一键会让人在不知情时再覆盖一次）；merge 语义（我们没有第二份库可合并）；整盘快照调度（kelivo 的 local snapshot 是另一件事，S2 再议）。

## 后果（Consequences）

- **正面**："恢复"第一次有出口；ADR-0042 的两段防线（验名 + 整体抛）之后补上第三段（可回滚）。
- **负面/风险**：恢复大归档多一次写放大（拷贝的是将被覆盖的文件，量级 = 归档本身）；`pre-restore/` 不进备份清单——副本的副本没有意义。
- **中性**：`BackupService` +2 静态方法；设置面板 +1 参数。

## 验证（Verification）

- `test/backup_paths_test.dart` 扩棵：恢复前快照存在且内容是旧字节；越界条目抛出时**没有**快照目录；第 4 份快照淘汰第 1 份；反向验过——删掉快照调用，"恢复成功但旧文件可寻"的断言红。
- 四道门禁同口径；真机走查恢复一次后到文件管理器找 `pre-restore/`。
